# DATA.md — 数据存储与查询指南

> 最后更新: 2026-10-25 · commit `c232168`

## 1. 数据实体清单

全部数据是**本机 Markdown / JSON / 锁文件**，集中在 `~/.opencode/`（core 层 **18 处** `join(homedir(), ".opencode", …)` 硬编码、**未参数化**；路径清单见 modules/store.md §文件族）。**OpenCode 与 DSH 共用这一份目录**——同一项目 slug 相同，画像与项目记忆真正跨宿主。

## 2. 格式

### USER.md（受管部分）

```markdown
# User Profile & Style

> Auto-generated by memx. Last updated: 2026-07-29

## 沟通与交互风格
- [2026-07-29] 先给结论，再展开推导过程

## 工具与环境偏好
- [2026-07-25] 使用 pnpm 而非 npm/yarn

## 踩坑与禁忌
- ~~[2026-07-15] 偏好 Vue 3 Composition API~~ (Deprecated: 已迁移至 Svelte)
```

规则：条目 `- [YYYY-MM-DD]` 开头；废弃用删除线不物理删除；四个固定分类标题不可新增；硬限 200 行。**非受管内容（preamble / section.extras）原样保留**。

### MEMORY.md 索引（受管格式 `- [title](path) - hook`）

```markdown
## root-project-foo
- [auth rewrite](~/.opencode/projects/root-project-foo/.mem/project_auth_rewrite.md) - auth middleware rewrite driven by compliance
```

### 记忆卡片

```markdown
---
name: auth rewrite
description: auth middleware rewrite driven by compliance
type: project
created: 2026-07-20
updated: 2026-07-29
---
Rewriting auth middleware for compliance.

**Why:** Legal flagged session token storage.
**How to apply:** Scope decisions favor compliance over ergonomics.
```

四类 type：`project`（进行中的工作）/ `reference`（外部资源指针）/ `feedback`（协作指导，强制 Why+How）/ `user`（用户背景）。

`created` / `updated` 是 UTC 日期（`YYYY-MM-DD`），由写盘层生成——**不进 `MemoryProposalSchema`**（LLM 不产时间戳）：新卡两者同日；update 在移走旧卡前读旧 frontmatter，`created` 原样保留、`updated` 刷新为今天。**老卡没有 `created:` 就保持缺失**，doctor 显示「未知龄期」——不伪造、也不用文件 mtime 兜底（update 会重置 mtime，sync pull 的 `copyFileSync` 也会重置）。

### slug 规则（`core/memory-types.ts` 的 `deriveSlug`）

目录路径去首尾 `/`、`/` → `-`。`/root/project/foo` → `root-project-foo`。

**空结果分两种，必须区分（#36 / #37）**：

| 入参 | 返回 | 含义 |
|------|------|------|
| `/`、`///` | `root` | 根目录会话（伴侣页 cwd 就是 `/`）→ 落 `projects/root/.mem/`，索引有 `## root` 节；**不拒写**（拒写会让"记一下"直接失效） |
| `""`、全空白 | `""` | 宿主取不到工作目录 = **未知**。DSH 壳拿空串当哨兵（`memory_write` 直接失败、`memory_search` 检索全库），不能被吞成 `root` |

归一只有这一处：cards 目录、索引节、注入、health、search 全部经 `deriveSlug` 派生。索引侧另有存量兼容：`## ` / `##`（空节头）在 `parseMemoryIndex` 里认领到 `root` 并与已有 `## root` 合并（详见 [modules/store.md](modules/store.md)）。

**工作目录路径避免空格/中文/特殊字符**，否则 slug 难看且难排查。

## 3. 常见查询场景

| 我想查 | 去哪 | 怎么查 |
|--------|------|--------|
| 画像现在记了什么 | `~/.opencode/USER.md` | 直接打开；废弃条目带删除线 |
| 某项目有哪些记忆 | `~/.opencode/MEMORY.md` 找 `## <slug>` 节 | 或打开对应 `.mem/` 目录 |
| 某条记忆的完整内容 | 索引里的链接 | 打开对应 `.mem/*.md` |
| 哪个文件哪一行提到某关键词 | 全部 `.mem/*.md` | 宿主工具 `memory_search`（DSH；大小写不敏感、返回 `slug/file:line`）——索引 slug ∪ 磁盘 slug，孤儿文件也能搜到 |
| 插件真实运行状态（OpenCode） | **sqlite kv 表**（不是 memx_status 的回执） | 见 §4 诊断 |
| 插件真实运行状态（DSH） | 宿主日志 | 搜 `[memx]`；`skipped.*` 计数解释"为什么没写"（disabled/duplicate/written/empty/throttle/noModel） |
| 某会话的捕获进度 | kv 的 `cursor:<sessionID>` | 同上（DSH 无游标） |
| 写坏了想回滚 | `~/.opencode/*.bak.<ts>` | 按时间戳选版本覆盖回去 |
| 被删掉的记忆 | `.mem/.trash/<file>.<ts>` | 改回文件名并重新登记索引 |
| 有哪些报警、要不要销账 | `~/.opencode/memx-alerts.json` | 或跑 `pnpm run doctor` 看 counts + 最近 10 条；销账 `pnpm alerts:clear --code=X` |
| 同步开了没、上次推拉何时 | `pnpm run doctor` 的 sync 段 | 或直读 `~/.opencode/memx-sync-state.json` |
| 哪些文件会被同步 | `pnpm sync:dry-run` | 只读预览（含双向行数 / PII 命中）；**永不 push** |
| 首合并前远端有什么 | `pnpm sync:dry-run -- --fetch` | 先取远端到 workdir（不碰 `~/.opencode` 记忆文件） |

## 4. 诊断查询（排查"它怎么又没记住"）

**第一步永远先跑 `pnpm run doctor`**——只读面板四段（alerts / memory files / opencode diag / sync），不联网、不写盘、退出码恒 0。⚠️ 别用 `pnpm doctor`（pnpm 有同名内建命令，会静默跑成 pnpm 自检）。

`memx_status` 工具只打固定字段；`evtCounts` / `lastCapture` / `rawContext` / `health` 只在 kv 行里（**`alerts` 例外**：以账本文件 `memx-alerts.json` 为准，kv 里那份是只写镜像）：

```bash
sqlite3 ~/.local/share/opencode/opencode.db \
  "SELECT value FROM kv WHERE key LIKE 'plugin:%'"
```

（namespace = `plugin:` + "memx" 逐字符 4 位十六进制；键已按目录隔离为 `diag:<slug>`。）注意：**同目录多实例仍会互相覆盖**（`opencode run --server` 客户端也会实例化插件），排查优先看 serve 日志：`~/.local/share/opencode/log/opencode.log`（成功写盘搜 `Updated USER.md` / `Updated MEMORY.md`；LLM 原始返回搜 `llm raw(N):`，400 字符截断）。

**DSH 侧没有 kv、没有 `memx_status`**：诊断只在进程内存（`DshDiagnostics`），异常与跳过原因落宿主日志（`ctx.logger.warn`，前缀 `[memx]`）。查"轮末为什么没写"看 `skipped.*` 的六类计数（`disabled` / `duplicate` / `written` / `empty` / `throttle` / `noModel`）——它们只在内存，重启即清零，所以要趁会话现场看日志。报警仍落同一份 `memx-alerts.json`（两宿主共用账本）。

## 5. 数据变更链路

| 谁写入 | 写到哪 | 谁读取 |
|--------|--------|--------|
| 后台提炼（SessionPipeline → refine/refineMemory） | USER.md / MEMORY.md + .mem | 下一 step / 下一会话的注入 |
| memory_write / forget 工具（OpenCode + DSH） | 同上（同一写入口 + 同一把锁） | 同上 |
| forget / deprecate | 移入 .trash + 索引改条目 | 注入的索引随之更新 |
| health auto-fix | MEMORY.md 索引（同锁内） | 同上 |
| memory_search（DSH 工具） | **不写盘**（只读 `.mem/*.md` + 索引） | 模型回执 |
| 报警（`recordAlert`） | `memx-alerts.json`（事实源）+ kv `diag.alerts`（镜像，仅 OpenCode）+ MEMORY.md 首行面包屑 | doctor / `memx_status` / **模型**（面包屑随索引被注入） |
| 云同步 push | `memx-sync-repo/` → 远端 Git 仓（USER.md / MEMORY.md / `.mem/**`） | 其他机器的 pull；状态被 doctor 读取 |
| 云同步 pull | 本地记忆文件（远端优先；本地差异先存 `.bak.<ts>`） | 下一 step / 下一会话的注入 |
| 主 AI（❗非 memx 行为） | 可能自行写 AGENTS.md 等文件 | 宿主指令组装——**这是所有权缺口，协议 v1.2.0 规则 9 是软约束** |

**多宿主并发**：文件锁（mtime TTL + 锁内重读）已覆盖"两个进程同时读改写同一文件"；DSH 与 OpenCode **已实际共享** `~/.opencode/`（core 里 18 处硬编码路径默认值一致）。注意两宿主的注入缓存语义不同：OpenCode 每 step 重算，DSH 每会话只算一次——所以 DSH 会话里看不到本会话刚写的记忆，这是设计语义，不是丢失。
